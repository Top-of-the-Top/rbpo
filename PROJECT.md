**Название продукта:** `Vedu`

**Статус ранней калибровки:** `согласовано`

**Требования безопасности:** [SECURITY_REQUIREMENTS.md](docs/SECURITY_REQUIREMENTS.md)  
**Модель угроз:** [THREAT_MODEL.md](docs/THREAT_MODEL.md)

## 1. Назначение

Продукт помогает небольшим командам организовать выполнение задач: автор задачи формулирует, что нужно сделать, назначает исполнителя, а по завершении проверяет результат и либо принимает его, либо отправляет на доработку. Результат получают все участники команды, они видят, кто чем занят и на каком этапе находится каждая задача. Предметная логика приложения состоит из модели жизненного цикла задачи (создание, выполнение, проверка, приёмка или доработка) и разграничения того, кто на каком этапе может её менять.

Основным интерфейсом служит доска команды с колонками по статусам задачи, устроенная по образцу привычных трекеров. Перенос карточки между колонками и есть смена статуса, поэтому проверка и приёмка не требуют отдельного экрана: автор закрывает задачу, перетаскивая её из колонки «На проверке» в «Готово», и возвращает на доработку обратным переносом. Сервер при каждом таком переносе проверяет, разрешён ли он этому пользователю в этой роли.

## 2. Граница продукта

**В продукт входит:**

- Регистрация и вход пользователей: отдельный логин на платформе, почта и пароль; вход по логину и паролю с подтверждением одноразовым кодом, отправляемым на почту (без OAuth и внешних провайдеров входа)
- Создание команд, управление составом (создатель команды добавляет/удаляет участников)
- Создание задач автором, назначение исполнителя
- Изменение статуса задачи исполнителем (например, «в работе», «выполнено»)
- Приёмка результата автором или возврат задачи на доработку
- Просмотр задач команды на доске с колонками по статусам, перенос карточек между колонками
- Приоритет задачи (низкий / обычный / высокий) и срок выполнения
- Подзадачи (простой чек-лист внутри задачи)
- Повторяющиеся задачи (следующий экземпляр создаётся после приёмки предыдущего)
- Второе представление задач команды: «Список» наряду с доской, переключение между ними
- Комментарии к задачам, упоминания участников команды (`@логин`, выбирается из участников) в комментариях
- Вложения файлов к задачам
- Обновление доски и списка у всех участников без перезагрузки страницы (работа в реальном времени)

**Внешнее окружение и внешние системы:**

- Почтовый сервис (SMTP): **обязателен**: отправляет одноразовые коды подтверждения при регистрации и входе; уведомления о новых задачах, смене статуса и упоминаниях это **опционально** (если будет реализовано). Для локального запуска и тестов отправитель писем заменяется заглушкой, которая пишет письмо в лог
- Хранилище пользовательских сессий/аутентификации

**Команда сознательно не реализует:**

- Спринты, эпики, диаграммы Ганта, отчёты о скорости команды и прочие инструменты полноценных систем управления проектами
- Настраиваемые пользователем колонки и произвольные схемы переходов: набор статусов фиксирован
- Трекинг времени и оценку трудозатрат
- Интеграции с внешними трекерами и сторонними сервисами
- Настраиваемые поля задач, шаблоны задач
- Гостевой и внешний доступ: любые действия только для зарегистрированных участников команды
- Календарь, таблицу, нагрузку, Mind map и прочие представления, кроме «Доски» и «Списка»
- Роли и права тоньше, чем «автор / исполнитель / участник команды»

Признаки сравнительного анализа, которые не вошли в границу, и причины отказа перечислены в [docs/USE_CASES.md §4.1.4](docs/USE_CASES.md).

## 3. Пользователи и доступные действия

| Пользователь или роль | Кто это | Что может делать | Что ему недоступно |
| --- | --- | --- | --- |
| Автор задачи | Участник команды, создавший конкретную задачу | Создавать задачи, назначать исполнителя, редактировать задачу, вести подзадачи и повторение, принимать результат, возвращать на доработку (с причиной), удалять свою задачу, прикреплять файлы, комментировать | Менять статус чужих задач как исполнитель, управлять составом команды (если не является её создателем), удалять чужие комментарии |
| Исполнитель | Участник команды, которому назначена задача | Менять статус своей задачи (взять в работу, передать на проверку), отмечать подзадачи, прикреплять файлы, комментировать, видеть детали задачи | Принимать/отклонять собственный результат, менять назначение и содержание задачи |
| Создатель команды | Участник, создавший команду | Добавлять и удалять участников команды, всё, что доступно автору задачи | Действия в чужих командах |
| Участник команды (наблюдатель) | Любой член команды без роли автора/исполнителя в конкретной задаче | Видеть доску и список команды со всеми задачами и их статусами, комментировать и упоминать участников, скачивать вложения | Перемещать чужие карточки между колонками, менять чужие задачи, прикреплять файлы к чужим задачам, создавать задачи от чужого имени |

Действий без входа в систему в этой предметной области нет: все операции требуют регистрации.

## 4. Сквозные сценарии

### Сценарий 1. Постановка и выполнение задачи

- **Участники:** автор задачи, исполнитель
- **Начальное условие:** оба состоят в одной команде
- **Основные действия:**
  1. Автор создаёт задачу с описанием, приоритетом и исполнителем
  2. Карточка появляется на доске команды в колонке «К выполнению»
  3. Исполнитель переносит её в «В работе»
  4. По завершении исполнитель переносит карточку в «На проверке»
- **Результат:** задача находится в колонке «На проверке» и ожидает решения автора
- **Какие данные или состояние изменяются:** создаётся запись задачи; меняется её статус и поле «исполнитель»

### Сценарий 2. Приёмка результата или возврат на доработку

- **Участники:** автор задачи, исполнитель
- **Начальное условие:** задача находится в колонке «На проверке»
- **Основные действия:**
  1. Автор открывает карточку и знакомится с результатом
  2. Автор переносит её в «Готово», если результат принят
  3. Либо возвращает карточку в «В работе», указав причину возврата
- **Результат:** задача либо закрывается, либо возвращается исполнителю для повторной работы
- **Какие данные или состояние изменяются:** статус задачи; при возврате также сохраняется запись в истории возвратов: причина, кто вернул и когда

### Сценарий 3. Формирование команды

- **Участники:** создатель команды, новый участник
- **Начальное условие:** пользователь зарегистрирован в системе
- **Основные действия:**
  1. Создатель команды добавляет пользователя в команду по логину
  2. Участник получает доступ к задачам команды
- **Результат:** участник видит доску команды и может быть назначен исполнителем
- **Какие данные или состояние изменяются:** список участников команды; связь между пользователем и командой

## 5. Значимые данные и другие объекты

| Данные или объект | Для кого имеют значение | Последствия раскрытия | Последствия неправильного изменения, удаления или недоступности |
| --- | --- | --- | --- |
| Задача (описание, статус, исполнитель, приоритет, срок) | Автор, исполнитель, команда | Утечка внутренних рабочих процессов команды посторонним | Потеря истории работы, путаница в статусах, срыв координации между автором и исполнителем |
| Учётные данные пользователя (логин, почта, пароль) | Все пользователи | Компрометация аккаунта, доступ к чужим командам и задачам от чужого имени | Невозможность входа, блокировка легитимного доступа |
| Состав команды (список участников) | Создатель команды, участники | Раскрытие структуры команды посторонним | Ошибочное назначение задач, потеря доступа нужных людей к задачам |
| Комментарии и вложения задач | Автор, исполнитель, участники команды | Утечка рабочих обсуждений и содержимого файлов (документы, скриншоты) посторонним | Потеря или подмена файлов, потеря причины возврата и контекста, подсовывание вредоносного файла участникам команды |
| Сессии и одноразовые коды входа | Все пользователи | Перехват сессии или кода даёт вход от чужого имени в обход пароля | Невозможность войти (код не приходит), «зависшие» сессии после выхода или удаления из команды |

## 6. Компоненты и внешние взаимодействия

Формальный архитектурный вид с потоками и границами доверия: [docs/THREAT_MODEL.md](docs/THREAT_MODEL.md#модель-продукта). Ниже — обзор обычным языком, включая части вне ядра модели угроз (комментарии, вложения, уведомления).

- **Клиент:** веб-интерфейс с доской и списком команды, карточками задач, переносом карточек между колонками, формами создания задачи, комментариев, загрузки файлов и управления составом команды, страницами регистрации и входа с вводом одноразового кода
- **Сервер (backend):** реализует логику жизненного цикла задачи, авторизацию и проверку прав (кто автор, кто исполнитель, кто участник команды), рассылку обновлений участникам
- **Хранилище (БД):** хранит пользователей, команды, задачи и их статусы, подзадачи, историю возвратов, комментарии, сведения о вложениях
- **Файловое хранилище:** хранит вложения; доступ к файлам только через сервер после проверки членства в команде
- **Аутентификация:** модуль регистрации и входа (логин, пароль, одноразовый код), может быть частью сервера или отдельным сервисом; хранит сессии
- **Почтовый сервис (внешний):** доставляет одноразовые коды на почту; в локальной среде заменяется заглушкой
- **Канал обновлений:** соединение сервера с открытой страницей клиента, по которому приходит сообщение «в команде что-то изменилось»; сами данные клиент запрашивает обычным запросом

Взаимодействие компонентов при любом изменении задачи:

1. Клиент отправляет запрос к серверу (создание задачи, перенос карточки, приёмка)
2. Сервер проверяет, допустим ли такой переход статуса и разрешён ли он этому пользователю в его роли
3. Сервер читает и записывает данные в БД
4. Сервер возвращает обновлённое состояние клиенту и сообщает об изменении другим участникам команды по каналу обновлений

Перенос карточки на доске не решает ничего сам: запрет на недопустимый переход проверяется на сервере, а клиент лишь возвращает карточку на место.

## 8. Минимальное функциональное ядро

**Обязательные функции:**

- Регистрация и вход (логин + почта + пароль + одноразовый код)
- Создание команды и добавление участников
- Создание задачи автором с назначением исполнителя
- Доска команды с колонками по статусам
- Смена статуса задачи исполнителем
- Приёмка/возврат на доработку автором **с обязательной причиной возврата**

**Функции, которые можно исключить при нехватке времени:**

- Перенос карточек мышью: статус можно менять кнопкой в карточке, доска остаётся
- Приоритеты и сроки задач
- Удаление участников из команды
- Уведомления (email/push) о задачах и упоминаниях (письма с кодами входа не исключаются)
- Редактирование и удаление задачи после создания
- Подзадачи, повторяющиеся задачи
- Представление «Список» (доска остаётся)
- Комментарии и упоминания, вложения файлов
- Обновление в реальном времени (доска обновляется по действию пользователя или повторному запросу)

После удаления необязательных функций сохраняются: серверная логика жизненного цикла задачи, три основных сценария, разграничение автор/исполнитель/участник и значимые данные (задача, пользователь, команда). Внешний вид доски можно упростить, но проверка допустимости перехода на сервере остаётся в любом случае, поскольку без неё исчезает предметная логика продукта.

## 9. Стек и путь к первой работающей версии

**Основные технологии:** Java 25 + Spring Boot на сервере: модульный монолит из двух Gradle-модулей: `api` (REST API и бизнес-логика; PostgreSQL через JPA и Flyway-миграции; Redis для одноразовых кодов и refresh-токенов) и `worker` (асинхронная обработка уведомлений, подписан на очередь). RabbitMQ брокер сообщений между `api` и `worker`. На клиенте React с TypeScript и Vite.

**Технологии, новые для команды:** Spring Boot, модульный монолит с выносом асинхронной части в отдельный сервис через брокер сообщений (RabbitMQ), Redis как хранилище одноразовых кодов и refresh-токенов, Flyway-миграции.

**Внешние сервисы, необходимые для запуска:** SMTP-сервер для писем с одноразовыми кодами (в проде); при локальном запуске и в тестах не нужен, тут используется заглушка отправки писем; уведомления о задачах опциональны

**Как основные сценарии будут запускаться и проверяться при недоступности внешних сервисов:** отправка писем скрыта за интерфейсом «отправитель писем» с двумя реализациями (SMTP и заглушка, пишущая письмо с кодом в лог), поэтому сценарии 1–3 и вход проверяются локально при поднятой БД

**Что команда реализует первым, чтобы получить запускаемую версию:** аутентификация: модель пользователя, PostgreSQL-хранилище через Flyway-миграции и REST API `/api/auth/*` (регистрация, вход, обновление и отзыв токенов); это уже реализовано. Следующий шаг: доменная модель команды и задачи с минимальным REST API для создания задачи и смены статуса с проверкой прав на сервере, без интерфейса или с заглушкой интерфейса.

## 10. Локальный запуск

**Требования к окружению:** Docker и Docker Compose (поднимает `api`, `worker`, PostgreSQL 17, Redis 8, RabbitMQ 4 с healthcheck'ами на все хранилища). Для сборки/тестов без контейнеров нужен JDK 25 и `./gradlew` (wrapper идёт в репозитории).

**Команды установки и запуска:**

```bash
cp .env.example .env   # заполнить JWT_SECRET, EMAIL_ENCRYPTION_KEY, EMAIL_IV_KEY и пароли БД/Redis/RabbitMQ
docker compose up --build
```

API поднимается на `http://localhost:8080`. Прогон тестов без подъёма стенда: `cd backend && ./gradlew test`.

**Команда или запрос для проверки:**

```bash
curl -i -X POST http://localhost:8080/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username":"demo_user","email":"demo@example.com","password":"password123"}'
```

**Ожидаемый результат:** `201 Created` с телом вида `{"accessToken":"...","refreshToken":"..."}`, значит, что учётная запись создана и выдана пара токенов. Повторный запрос с тем же `username` или `email` завершается ошибкой (логин/почта уже заняты).

*Эта проверка подтверждает запуск и базовую регистрацию, а не выполнение всех требований безопасности.*
