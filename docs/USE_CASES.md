# Варианты использования (Use Cases)

Раздел детализирует сквозные сценарии [PROJECT.md §4](../PROJECT.md) до отдельных вариантов использования. Состав выведен из сравнительного анализа 8 платформ по 52 признакам, выполненного с помощью ИИ (описание — в [AI_USAGE.md](../AI_USAGE.md), результат — в §4.1.4 ниже): взяты признаки категорий 1–3, полностью реализованные (●) минимум у 5 из 8 платформ, за вычетом признаков, вынесенных за границу продукта (§4.1.4). Структура данных, форматы и числовые ограничения здесь намеренно не описываются — они определяются при проектировании.

## 4.1.1. Общие правила

- **Идентификация.** Пользователь идентифицируется уникальным логином на платформе и отображается именем. Адрес электронной почты нужен для одноразовых кодов и уведомлений; по нему пользователей не ищут и не входят. Логин виден участникам команд и используется при добавлении в команду и в упоминаниях.
- **Статусы задачи (фиксированы):** «К выполнению» → «В работе» → «На проверке» → «Готово». Возврат на доработку — переход «На проверке» → «В работе».
- **Проверки на сервере.** Каждая операция, кроме регистрации и входа, проходит проверки в таком порядке: пользователь вошёл → состоит в команде объекта → его роль разрешает действие → данные корректны → состояние объекта допускает действие. При любом отказе состояние не меняется. Для не-участника команды её объекты «не существуют».
- **Клиент не решает, что разрешено.** Кнопки могут скрываться по подсказке сервера, но каждое действие проверяется заново. Автор, исполнитель и прочие «кто» всегда определяются из сессии, а не из запроса.
- **Устаревшее состояние.** Если задача изменилась, пока пользователь готовил действие, действие отклоняется и пользователю показывается актуальное состояние.
- **Просроченные задачи** (срок прошёл, статус не «Готово») помечаются на карточке.

## 4.1.2. Матрицы прав и переходов

**Кто что может** (в отношении одной задачи; создатель команды в отношении чужих задач имеет права рядового участника):

| Операция | Автор задачи | Исполнитель | Участник команды | Создатель команды |
| --- | --- | --- | --- | --- |
| Видеть доску, список, карточку, комментарии, вложения | да | да | да | да |
| Создать задачу в команде (становится её автором) | да | да | да | да |
| Редактировать задачу, менять исполнителя, повторение, подзадачи | да | нет | нет | нет |
| Удалить задачу | да | нет | нет | нет |
| «К выполнению» → «В работе», «В работе» → «На проверке» | нет | да | нет | нет |
| «На проверке» → «Готово» или возврат в «В работе» с причиной | да | нет | нет | нет |
| Отмечать подзадачи выполненными | да | да | нет | нет |
| Комментировать | да | да | да | да |
| Удалять комментарий | свой | свой | свой | свой |
| Прикреплять файл | да | да | нет | нет |
| Скачивать вложение | да | да | да | да |
| Удалять вложение | любое | своё | нет | нет |
| Добавлять и удалять участников команды | нет | нет | нет | да |

Автор и исполнитель одной задачи — разные пользователи (допущение 2 в §4.1.5), поэтому исполнитель не может принять собственный результат.

**Допустимые переходы статуса** (любой другой переход отклоняется):

| Из | В | Кто | Условие |
| --- | --- | --- | --- |
| К выполнению | В работе | исполнитель | — |
| В работе | На проверке | исполнитель | — |
| На проверке | Готово | автор | — |
| На проверке | В работе | автор | указана причина возврата |

Из «Готово» выхода нет: закрытая задача не редактируется и не переоткрывается. Перенос карточки мышью и кнопка в карточке вызывают одну и ту же серверную операцию; при отказе клиент возвращает карточку на место.

## 4.1.3. Use cases

**Приоритет реализации:** «ядро» — входит в минимальное ядро ([PROJECT.md §8](../PROJECT.md)), «расширенный» — можно отложить. **Связь** — признак сравнительного анализа или сквозной сценарий.

### Группа A. Учётная запись и аутентификация

Авторизация (кто что может) — это проверки в каждой операции ниже, аутентификация (кто это) — только эта группа. Одноразовый код (OTP) везде работает одинаково: одноразовый, с ограниченным временем жизни и числом попыток, хранится в необратимом виде.

#### UC-01. Регистрация с подтверждением почты

- **Актор:** новый пользователь
- **Приоритет реализации:** ядро
- **Предусловия:** пользователь не вошёл; у него есть доступ к указанной почте
- **Основной сценарий:**
  1. Пользователь вводит логин, почту, имя и пароль
  2. Система проверяет данные и уникальность логина
  3. Система создаёт неподтверждённую учётную запись, пароль сохраняется только в необратимом виде
  4. Система отправляет одноразовый код на почту
  5. Пользователь вводит код
  6. Система подтверждает учётную запись и выполняет вход
- **Альтернативные сценарии:**
  - 2а. Данные некорректны — форма показывает ошибки
  - 2б. Логин занят — пользователю предлагается выбрать другой
  - 3а. Почта уже принадлежит другой учётной записи — ответ не отличается от успешного (наличие учётной записи не раскрывается), владельцу адреса уходит письмо
  - 5а. Код неверный или просрочен — вход не выполняется; после нескольких неверных попыток код аннулируется, нужно запросить новый
  - 5б. Пользователь запрашивает код повторно — допускается с ограничением частоты
- **Постусловия:** создана активная учётная запись, пользователь вошёл

#### UC-02. Вход по логину и паролю с одноразовым кодом

- **Актор:** зарегистрированный пользователь
- **Приоритет реализации:** ядро
- **Предусловия:** активная учётная запись; пользователь не вошёл
- **Основной сценарий:**
  1. Пользователь вводит логин и пароль
  2. Система проверяет пароль
  3. Система отправляет одноразовый код на почту, указанную при регистрации
  4. Пользователь вводит код
  5. Система проверяет код и создаёт сессию
- **Альтернативные сценарии:**
  - 2а. Логин не найден, пароль неверный или учётная запись не подтверждена — единое сообщение «неверный логин или пароль»
  - 2б. Слишком много неудачных попыток — вход временно блокируется
  - 4а. Код неверный, просрочен или исчерпаны попытки — вход прерывается, начинается заново
  - 4б. Повторная отправка кода — по правилам UC-01 (5б)
- **Постусловия:** пользователь аутентифицирован, создана сессия
- **Связь:** все остальные use case'ы опираются на действующую сессию

#### UC-03. Выход

- **Актор:** аутентифицированный пользователь
- **Приоритет реализации:** ядро
- **Предусловия:** действующая сессия
- **Основной сценарий:** пользователь нажимает «Выйти»; система завершает сессию; открывается страница входа
- **Альтернативные сценарии:** сессия уже недействительна — выход завершается без ошибки
- **Постусловия:** прежняя сессия больше не принимается; соединение реального времени (UC-23) закрыто

### Группа B. Команды

#### UC-04. Создание команды

- **Актор:** аутентифицированный пользователь
- **Приоритет реализации:** ядро
- **Предусловия:** пользователь вошёл
- **Основной сценарий:**
  1. Пользователь вводит название команды
  2. Система создаёт команду, пользователь становится её создателем и участником
  3. Открывается пустая доска команды (UC-20)
- **Альтернативные сценарии:** название пустое — форма показывает ошибку
- **Постусловия:** существует команда; состав меняет только её создатель
- **Связь:** сценарий 3

#### UC-05. Просмотр своих команд и выбор команды

- **Актор:** аутентифицированный пользователь
- **Приоритет реализации:** ядро
- **Предусловия:** пользователь вошёл
- **Основной сценарий:** система показывает команды пользователя с его ролью («создатель» или «участник»); пользователь выбирает команду; открывается доска (UC-20)
- **Альтернативные сценарии:** команд нет — предлагается создать команду (UC-04); чужие команды не показываются
- **Постусловия:** состояние не меняется

#### UC-06. Добавление участника в команду

- **Актор:** создатель команды
- **Приоритет реализации:** ядро
- **Предусловия:** добавляемый пользователь зарегистрирован и подтвердил почту
- **Основной сценарий:**
  1. Создатель вводит логин добавляемого пользователя
  2. Система проверяет, что операцию выполняет создатель этой команды
  3. Система добавляет пользователя в команду сразу, без приглашения и подтверждения
  4. Пользователь видит команду в своём списке (UC-05) и может быть назначен исполнителем
- **Альтернативные сценарии:**
  - 2а. Операцию выполняет не создатель — отказ, состав не меняется
  - 3а. Пользователь с таким логином не найден — создателю сообщается об этом
  - 3б. Пользователь уже в команде — сообщение об этом
- **Постусловия:** в команде на одного участника больше
- **Связь:** сценарий 3

#### UC-07. Удаление участника из команды

- **Актор:** создатель команды
- **Приоритет реализации:** расширенный
- **Предусловия:** участник не является создателем команды
- **Основной сценарий:**
  1. Создатель выбирает участника и подтверждает удаление
  2. Система проверяет права создателя
  3. Система проверяет, что у участника нет незавершённых задач (как у автора или исполнителя)
  4. Участник удаляется; он теряет доступ к доске, карточкам, комментариям и вложениям команды
- **Альтернативные сценарии:**
  - 2а. Операцию выполняет не создатель — отказ
  - 3а. У участника есть незавершённые задачи — удаление отклоняется, создателю показывается список задач; их нужно сначала переназначить или удалить
  - 3б. Удаляется сам создатель — отказ (передачи команды в продукте нет)
- **Постусловия:** участник вне команды; его прошлые комментарии и закрытые задачи сохраняются

### Группа C. Задачи

#### UC-08. Создание задачи

- **Актор:** участник команды (становится автором)
- **Приоритет реализации:** ядро (приоритет и срок можно отложить)
- **Предусловия:** пользователь — участник команды; в команде есть ещё хотя бы один участник, которого можно назначить исполнителем
- **Основной сценарий:**
  1. Пользователь заполняет название, описание, исполнителя из участников команды, приоритет (по умолчанию «обычный») и срок
  2. Система проверяет членство пользователя в команде и корректность полей
  3. Система создаёт задачу в статусе «К выполнению»; автором записывается пользователь из сессии
  4. Карточка появляется на доске всех участников (UC-23)
- **Альтернативные сценарии:**
  - 2а. Исполнитель не из этой команды или совпадает с автором — форма показывает ошибку
  - 2б. Название пустое — форма показывает ошибку
  - 2в. В запросе указан другой автор — он игнорируется, автором становится пользователь из сессии
  - 2г. Срок в прошлом допустим (вносится уже начатая работа); задача помечается просроченной
- **Постусловия:** создана задача «К выполнению»
- **Связь:** «Создание задачи», «Приоритет»; сценарий 1

#### UC-09. Просмотр карточки задачи

- **Актор:** любой участник команды
- **Приоритет реализации:** ядро
- **Предусловия:** пользователь вошёл
- **Основной сценарий:** пользователь открывает карточку с доски или из списка; система показывает поля задачи, автора, исполнителя, подзадачи, историю возвратов на доработку (причина, кто, когда), комментарии, вложения и доступные этому пользователю действия
- **Альтернативные сценарии:** задача удалена или принадлежит чужой команде — для пользователя её не существует
- **Постусловия:** состояние не меняется

#### UC-10. Редактирование задачи и смена исполнителя

- **Актор:** автор задачи
- **Приоритет реализации:** расширенный ([PROJECT.md §8](../PROJECT.md))
- **Предусловия:** задача не в статусе «Готово»
- **Основной сценарий:**
  1. Автор меняет название, описание, приоритет, срок, повторение (UC-18) или исполнителя
  2. Система проверяет, что пользователь — автор этой задачи
  3. Система сохраняет изменения
- **Альтернативные сценарии:**
  - 2а. Пользователь не автор — отказ, поля не меняются
  - 2б. Задача в «Готово» — отказ
  - 3а. Смена исполнителя разрешена только пока задача в «К выполнению»
  - 3б. Новый исполнитель совпадает с автором или не из команды — ошибка
  - 3в. Задача изменилась, пока автор редактировал — изменения отклоняются, показывается актуальное состояние
- **Постусловия:** поля обновлены; статус не меняется (статус меняют только UC-12…UC-15)
- **Связь:** «Назначение задачи», «Приоритет»

#### UC-11. Удаление задачи

- **Актор:** автор задачи
- **Приоритет реализации:** расширенный
- **Предусловия:** пользователь вошёл
- **Основной сценарий:**
  1. Автор выбирает «Удалить» и подтверждает
  2. Система проверяет, что пользователь — автор
  3. Система удаляет задачу; вложения перестают быть доступны
  4. Карточка исчезает у всех участников (UC-23)
- **Альтернативные сценарии:**
  - 2а. Пользователь не автор — отказ
  - 3а. Удаляется повторяющаяся задача — цепочка повторений прекращается
  - 3б. Удаление возможно в любом статусе, включая «Готово»
- **Постусловия:** задача не видна ни в доске, ни в списке; история возвратов сохраняется в хранилище

### Группа D. Жизненный цикл задачи

Все четыре use case'а — одна серверная операция «сменить статус» (§4.1.2), доступная кнопкой в карточке и перетаскиванием карточки. При любом отказе статус не меняется, клиент возвращает карточку на прежнее место.

#### UC-12. Взять задачу в работу

- **Актор:** исполнитель задачи
- **Приоритет реализации:** ядро
- **Предусловия:** задача в статусе «К выполнению»
- **Основной сценарий:** исполнитель нажимает «Взять в работу» или переносит карточку в «В работе»; система проверяет, что он назначенный исполнитель; статус становится «В работе»
- **Альтернативные сценарии:** пользователь не исполнитель — отказ; статус уже не «К выполнению» или задача изменилась — отказ с показом актуального состояния
- **Постусловия:** задача «В работе»
- **Связь:** сценарий 1; «Базовые статусы», «Перетаскивание»

#### UC-13. Передать задачу на проверку

- **Актор:** исполнитель задачи
- **Приоритет реализации:** ядро
- **Предусловия:** задача в статусе «В работе»
- **Основной сценарий:** исполнитель нажимает «Готово к проверке» или переносит карточку в «На проверке»; система проверяет исполнителя; статус становится «На проверке»
- **Альтернативные сценарии:** как в UC-12; невыполненные подзадачи передачу не блокируют — подзадачи служат памяткой и не влияют на жизненный цикл
- **Постусловия:** задача ожидает решения автора
- **Связь:** сценарий 1

#### UC-14. Принять результат

- **Актор:** автор задачи
- **Приоритет реализации:** ядро
- **Предусловия:** задача в статусе «На проверке»
- **Основной сценарий:** автор проверяет результат по карточке (UC-09) и нажимает «Принять» или переносит карточку в «Готово»; система проверяет, что он автор; статус становится «Готово»; если у задачи включено повторение, создаётся следующий экземпляр (UC-19)
- **Альтернативные сценарии:** исполнитель или другой участник — отказ, задача остаётся «На проверке»; задача не «На проверке» — отказ, в том числе попытка перейти из «В работе» сразу в «Готово»
- **Постусловия:** задача закрыта и больше не редактируется
- **Связь:** сценарий 2

#### UC-15. Вернуть задачу на доработку

- **Актор:** автор задачи
- **Приоритет реализации:** ядро
- **Предусловия:** задача в статусе «На проверке»
- **Основной сценарий:**
  1. Автор нажимает «Вернуть на доработку» или переносит карточку из «На проверке» в «В работе»; система запрашивает причину
  2. Автор вводит причину
  3. Система проверяет, что пользователь — автор, и что причина не пуста
  4. Система меняет статус на «В работе» и сохраняет причину, автора возврата и время
  5. Исполнитель видит карточку в «В работе» с причиной возврата
- **Альтернативные сценарии:**
  - 3а. Причина пуста — возврат не выполняется, статус не меняется
  - 3б. Пользователь не автор — отказ
  - 1а. Карточка перенесена мышью без причины — перенос отменяется, открывается ввод причины
- **Постусловия:** задача «В работе»; комментарии, вложения и подзадачи сохранены; история возвратов пополнена
- **Связь:** сценарий 2

### Группа E. Подзадачи

#### UC-16. Управление подзадачами

- **Актор:** автор задачи
- **Приоритет реализации:** расширенный
- **Предусловия:** задача не в статусе «Готово»
- **Основной сценарий:** автор добавляет, переименовывает, удаляет или упорядочивает подзадачи в карточке; система проверяет, что он автор, и сохраняет
- **Правила:** подзадача — это только название и отметка «выполнена»; у неё нет своего исполнителя, срока, статуса и комментариев; вложенности глубже одного уровня нет
- **Альтернативные сценарии:** пользователь не автор или задача «Готово» — отказ; пустое название — ошибка
- **Постусловия:** список подзадач изменён; статус задачи не меняется
- **Связь:** «Подзадачи»

#### UC-17. Отметить подзадачу выполненной

- **Актор:** исполнитель или автор задачи
- **Приоритет реализации:** расширенный
- **Предусловия:** задача не в статусе «Готово»
- **Основной сценарий:** пользователь ставит или снимает отметку у подзадачи; система проверяет, что он автор или исполнитель этой задачи; на карточке обновляется прогресс «выполнено N из M»
- **Альтернативные сценарии:** другой участник или задача «Готово» — отказ
- **Постусловия:** отметка изменена; статус задачи не меняется автоматически
- **Связь:** «Подзадачи»

### Группа F. Повторяющиеся задачи

#### UC-18. Настроить повторение задачи

- **Актор:** автор задачи
- **Приоритет реализации:** расширенный
- **Предусловия:** задача не в статусе «Готово»; у задачи задан срок
- **Основной сценарий:** автор выбирает периодичность (ежедневно, еженедельно, ежемесячно) или «не повторять»; система проверяет, что он автор и срок задан; сохраняет настройку
- **Альтернативные сценарии:** не автор или задача «Готово» — отказ; срок не задан — ошибка; выбор «не повторять» прекращает цепочку
- **Постусловия:** после приёмки задачи (UC-14) будет создан следующий экземпляр (UC-19)
- **Связь:** «Повторяющиеся задачи»

#### UC-19. Автоматическое создание следующего экземпляра (системное действие)

- **Актор:** система (срабатывает при приёмке, UC-14)
- **Приоритет реализации:** расширенный
- **Предусловия:** принята задача с включённым повторением
- **Основной сценарий:** система создаёт новую задачу с тем же автором, исполнителем, названием, описанием, приоритетом и повторением; подзадачи копируются невыполненными; статус «К выполнению»; срок сдвигается на период повторения от предыдущего срока
- **Правила:** создаётся ровно один экземпляр; комментарии, вложения и история возвратов не копируются; приёмка и создание следующего экземпляра выполняются вместе — если создание не удалось, приёмка отменяется; повторение запускается приёмкой, а не временем, поэтому планировщик не нужен (проектное решение)
- **Альтернативные сценарии:** срок нового экземпляра оказался в прошлом — экземпляр создаётся с этим сроком и помечается просроченным, «догоняющих» экземпляров нет
- **Постусловия:** в «К выполнению» появилась новая карточка; участники видят её (UC-23)

### Группа G. Представления

#### UC-20. Просмотр доски команды

- **Актор:** любой участник команды
- **Приоритет реализации:** ядро
- **Предусловия:** пользователь выбрал команду (UC-05)
- **Основной сценарий:** система проверяет членство и показывает задачи команды по четырём колонкам; на карточке — название, исполнитель, приоритет, срок и признак просрочки, прогресс подзадач, наличие комментариев и вложений; открывается канал обновлений (UC-23)
- **Альтернативные сценарии:** пользователь не участник команды — команды для него не существует; в колонке «Готово» показываются только недавно закрытые задачи, остальные доступны в «Списке»
- **Постусловия:** состояние не меняется
- **Связь:** «Kanban-доска»

#### UC-21. Просмотр списка задач

- **Актор:** любой участник команды
- **Приоритет реализации:** расширенный
- **Предусловия:** пользователь выбрал команду (UC-05)
- **Основной сценарий:** система проверяет членство и показывает все задачи команды таблицей: название, статус, приоритет, исполнитель, автор, срок; пользователь сортирует по любому столбцу; из списка доступны те же действия над задачей (UC-12…UC-15) с теми же проверками
- **Альтернативные сценарии:** пользователь не участник — команды для него не существует; фильтрация и поиск в объём не входят (§4.1.5)
- **Постусловия:** состояние не меняется
- **Связь:** «Список»

#### UC-22. Переключение между доской и списком

- **Актор:** любой участник команды
- **Приоритет реализации:** расширенный
- **Предусловия:** пользователь выбрал команду
- **Основной сценарий:** пользователь переключателем «Доска / Список» выбирает вид; система показывает те же задачи в выбранном виде (UC-20 или UC-21)
- **Правила:** права и видимые данные в обоих видах одинаковы; выбранный вид не хранится на сервере и не влияет на права
- **Постусловия:** серверное состояние не меняется
- **Связь:** «Несколько представлений на проект»

#### UC-23. Обновление доски и списка в реальном времени (системное действие)

- **Актор:** система → подключённые участники команды
- **Приоритет реализации:** расширенный ([PROJECT.md §8](../PROJECT.md))
- **Предусловия:** пользователь вошёл и открыл доску или список
- **Основной сценарий:**
  1. Открытая страница подключается к каналу обновлений своей команды; система проверяет вход и членство в команде
  2. Когда кто-либо из участников меняет команду (создаёт, редактирует, удаляет или переводит задачу, комментирует, прикрепляет файл, меняет состав), система уведомляет подключённых участников
  3. Страница запрашивает актуальные данные и обновляет доску или список
- **Альтернативные сценарии:**
  - 2а. Соединение прервалось — страница переподключается и заново загружает данные целиком (источник правды — сервер)
  - 2б. Пользователь удалён из команды или вышел из системы — подключение закрывается
  - 3а. Уведомление не содержит данных задачи: сами данные страница получает обычным запросом с полной проверкой прав
- **Постусловия:** серверное состояние не меняется
- **Связь:** «Совместная работа в реальном времени»

### Группа H. Комментарии и вложения

#### UC-24. Добавить комментарий и упомянуть участника

- **Актор:** любой участник команды
- **Приоритет реализации:** расширенный
- **Предусловия:** задача существует; комментировать можно в любом статусе, включая «Готово»
- **Основной сценарий:**
  1. Пользователь пишет текст и при вводе `@` выбирает участника команды по логину из подсказки
  2. Система проверяет членство пользователя, что текст не пуст и что упомянутые — участники этой же команды
  3. Система сохраняет комментарий с автором из сессии и временем
  4. Комментарий появляется у всех участников (UC-23); упомянутый видит отметку (письмо — если будут реализованы уведомления)
- **Альтернативные сценарии:**
  - 2а. Текст пуст — ошибка
  - 2б. Упомянутый не из команды — упоминание не создаётся, текст остаётся обычным
- **Правила:** причина возврата на доработку (UC-15) — не комментарий; комментарии не редактируются
- **Постусловия:** добавлен комментарий
- **Связь:** «Комментарии», «Упоминания»

#### UC-25. Удалить свой комментарий

- **Актор:** автор комментария
- **Приоритет реализации:** расширенный
- **Предусловия:** комментарий существует
- **Основной сценарий:** автор комментария нажимает «Удалить»; система проверяет, что комментарий его; комментарий исчезает у всех участников (UC-23)
- **Альтернативные сценарии:** чужой комментарий — отказ; автор задачи чужие комментарии не удаляет (роли не тоньше [PROJECT.md §2](../PROJECT.md))
- **Постусловия:** комментарий удалён

#### UC-26. Прикрепить файл к задаче

- **Актор:** автор или исполнитель задачи
- **Приоритет реализации:** расширенный
- **Предусловия:** задача не в статусе «Готово»
- **Основной сценарий:**
  1. Пользователь выбирает файл
  2. Система проверяет роль (автор или исполнитель), допустимость типа, размера и количества вложений
  3. Система сохраняет файл и показывает его в карточке
  4. Вложение появляется у всех участников (UC-23)
- **Альтернативные сценарии:**
  - 2а. Роль не подходит или задача «Готово» — отказ
  - 2б. Файл не соответствует ограничениям на тип, размер или количество — отказ с пояснением
- **Постусловия:** файл доступен только участникам команды и только через UC-27
- **Связь:** «Вложения файлов»

#### UC-27. Скачать вложение

- **Актор:** любой участник команды
- **Приоритет реализации:** расширенный
- **Предусловия:** вложение существует
- **Основной сценарий:** пользователь нажимает на вложение; система проверяет вход и членство в команде задачи и отдаёт файл на скачивание
- **Альтернативные сценарии:** вложение удалено или пользователь не участник команды — для него вложения не существует; публичных ссылок на файлы нет
- **Постусловия:** состояние не меняется

#### UC-28. Удалить вложение

- **Актор:** загрузивший пользователь или автор задачи
- **Приоритет реализации:** расширенный
- **Предусловия:** задача не в статусе «Готово»
- **Основной сценарий:** пользователь нажимает «Удалить» у вложения; система проверяет, что он загрузивший или автор задачи; вложение удаляется и исчезает у всех участников (UC-23)
- **Альтернативные сценарии:** исполнитель пытается удалить чужое вложение — отказ; задача «Готово» — отказ
- **Постусловия:** вложение удалено

## 4.1.5. Допущения и открытые вопросы

Допущения, принятые при описании (нужно подтвердить):

1. **Одноразовый код** требуется и при регистрации, и при каждом входе после пароля. Если только при регистрации, UC-02 упрощается до «логин + пароль».
2. **Автор ≠ исполнитель:** автор не назначает исполнителем себя, иначе приёмка своего результата теряет смысл.
3. **Права создателя команды** в отношении чужих задач — как у рядового участника ([PROJECT.md §3](../PROJECT.md) формулирует «всё, что доступно автору задачи» неоднозначно).
4. **Удаление участника** с незавершёнными задачами запрещено (UC-07), а не передаёт задачи автоматически.
5. **Смена исполнителя** возможна только в статусе «К выполнению» (UC-10).
6. **Удаление задачи** сохраняет историю возвратов (UC-11).

Открытые вопросы:

- Нужно ли восстановление пароля и смена пароля или почты? В объём не вошли.
- Нужна ли фильтрация и поиск в «Списке»? Сейчас только сортировка.
- Нужна ли проверка файлов на вирусы и квота вложений на команду?
- Документ требований безопасности не покрывает одноразовые коды, сессии, комментарии, вложения и реальное время — их стоит добавить отдельным шагом.
- Почтовый сервис обязателен для входа: при недоступности SMTP войти нельзя.
